# Разработка

## Принято: стек и стиль

Язык — Go 1.27, module path — `github.com/ruwcs/wcs-guide`. Используется актуальное исправление ветки 1.27.x; при подготовке окружения и обновлении сборок проверяются [актуальные выпуски Go](https://go.dev/doc/devel/release).

Приложение должно собираться с `CGO_ENABLED=0`; драйвер SQLite выбирается с учётом этого ограничения. Предпочтительна стандартная библиотека, в частности `net/http`, `html/template`, `database/sql`, `log/slog` и `context`. [Архитектурные ограничения](architecture.md) важнее внешнего сходства с крупными CMS.

Код простой, явный и читаемый. Пакеты выделяются по реальным обязанностям, без обязательного пакета для каждой сущности. Интерфейсы вводятся там, где нужен контракт потребителю, а не ради архитектурного шаблона. Не переносить механически подходы Java/C#, не вводить сложный DI, рефлексию, метапрограммирование и обобщения без веской причины. Дженерики не являются целью сами по себе.

Ошибки обрабатываются явно, с полезным контекстом и без утечки секретов. Контексты передаются операциям, поддерживающим отмену; запросы и фоновые операции имеют ограниченные сроки. Нельзя прятать сетевую операцию без таймаута за интерфейсом.

Вся проектная документация, комментарии в коде и документационные комментарии к пакетам, типам, функциям и методам пишутся по-русски. Идентификаторы, имена пакетов, файлов и технических сущностей — по-английски. Комментарии объясняют назначение, контракт, ограничения и неочевидные причины, не пересказывают код. Официальные лицензии и уведомления сторонних авторов сохраняются в оригинале.

Каждое поле структуры обязательно сопровождается коротким русским комментарием о назначении рядом с объявлением. Это относится также к вспомогательным типам и анонимным структурам в тестах. Существенную семантику нулевого значения уточняйте в том же комментарии, без пересказа всей модели.

```go
SourceID int64 // Источник, которому принадлежит снимок.
```

Комментарий метода, реализующего интерфейс, называет точный интерфейс и тип. Дополнительное описание требуется только для существенных особенностей реализации, например конкретного способа хранения. Для вспомогательных методов достаточно:

```go
// LogValue реализует интерфейс slog.LogValuer для Block.
// String реализует интерфейс fmt.Stringer для PageStatus.
```

## Принято: зависимости и логирование

Библиотеки выбираются непосредственно перед соответствующей функциональностью. Проверяются зрелость, поддержка, совместимость с Go, сборкой без CGO и AGPL v3. Зависимость должна решать конкретную задачу; заранее добавлять SQLite-, Telegram-, WebAuthn- или Markdown-библиотеки не требуется.

Логирование — через `log/slog`. Основные сущности приложения обязаны реализовывать интерфейс `slog.LogValuer`. Для вспомогательных типов, DTO, параметров операций и других служебных структур реализация не обязательна. Перечень основных сущностей, реализующих интерфейс, формируется по мере реализации модели; исчерпывающий список заранее не устанавливается.

Метод `LogValue` должен возвращать компактный и безопасный набор значимых атрибутов сущности, например идентификатор и тип. Не включать секреты, токены, содержимое материалов, чувствительные параметры конфигурации и другие потенциально конфиденциальные данные. Не логировать сущность целиком автоматически.

Журнал действий из [auth.md](auth.md) не следует считать автоматически обеспеченным техническими логами. Политику хранения и доступ к нему определить при реализации.

## Принято: Git

[Репозиторий](https://github.com/ruwcs/wcs-guide) публичный. `main` — ветка по умолчанию и релизное состояние; `dev` — повседневная разработка. После клонирования для обычной работы нужно переключиться в `dev`.

Короткие рабочие ветки при необходимости направляются в `dev`, а не в `main`. Обязательная сложная модель ветвления не вводится. Состояние первоначальной подготовки репозитория отражено в [roadmap.md](roadmap.md).

Никогда не создавать коммиты и не выполнять push без прямого указания пользователя на соответствующее действие. Просьба изменить файлы или выполнить задачу не является разрешением на commit или push. Это постоянное правило закреплено в [AGENTS.md](../AGENTS.md).

После прямого указания создать коммиты группируйте изменения по смыслу: один коммит — логически цельное изменение. Независимые задачи разделяйте; связанные код, тесты и документация могут входить в один коммит. Не объединяйте всю рабочую копию автоматически и не дробите изменения механически по файлам.

Не сливать в `main`, не создавать релизные теги и не публиковать релизы без явного указания владельца. Не выполнять force push и деструктивные операции Git без явного согласования. Перед изменениями проверять состояние дерева и не перезаписывать чужую работу. Порядок релиза находится в [releases.md](releases.md).

Секреты, рабочие конфигурации, реальные БД, Telegram-сессии и снимки не включаются в Git даже временно. Для примеров и тестов используются синтетические или специально разрешённые обезличенные данные. `.gitignore` снижает риск случайного добавления, но не защищает уже отслеживаемые файлы и не заменяет просмотр diff.

## Принято: проверки

Для изменений документации проверяются полнота, согласованность, локальные ссылки, сохранность официальной лицензии и отсутствие секретов. Форматирование отслеживаемых изменений проверяется через `git diff --check`; неотслеживаемые файлы нужно проверить отдельно без добавления в индекс. Не создавать `go.mod`, тесты и инструменты ради формального запуска Go-команд.

После появления Go-кода минимальные проверки, применимые к изменению:

```sh
gofmt -l .
CGO_ENABLED=0 go test ./...
CGO_ENABLED=0 go vet ./...
CGO_ENABLED=0 go build ./...
```

Вывод `gofmt -l` должен быть пустым; форматирование исправляется до коммита. Дополнительные проверки назначаются по риску изменения. Проверка гонок выполняется отдельно в подходящем окружении: race detector не является частью обязательной сборки без CGO.

Тестируются значимые контракты: отсутствие новой версии при неизменившемся источнике, сохранение последнего результата при ошибке, безопасный вывод, конкурентное использование приглашения, отзыв доступа и согласованность публикации. Сценарии приёмки редакционного жизненного цикла и публичного представления приведены в [roadmap.md](roadmap.md). Высокий процент покрытия не является самостоятельной целью. В отчёте указываются выполненные проверки и то, что пока невозможно проверить.

## Решить перед реализацией

Минимальную структуру пакетов и команд, зависимости, команды локального запуска, конфигурацию и конкретные проверки добавлять вместе с работающей функциональностью. Dockerfile, workflows и миграции создаются на соответствующем этапе реализации; инструкции запуска должны описывать доступное поведение. Порядок и состояние этапов находятся в [roadmap.md](roadmap.md).
