# Разработка

## Принято: стек и стиль

Язык — Go 1.27, module path — `github.com/ruwcs/wcs-guide`. Используется актуальное
исправление ветки 1.27.x; при подготовке окружения и обновлении сборок проверяются
[актуальные выпуски Go](https://go.dev/doc/devel/release).

Приложение должно собираться с `CGO_ENABLED=0`; драйвер SQLite выбирается с учётом этого
ограничения. Предпочтительна стандартная библиотека, в частности `net/http`, `html/template`,
`database/sql`, `log/slog` и `context`. [Архитектурные ограничения](architecture.md) важнее
внешнего сходства с крупными CMS.

Код простой, явный и читаемый. Пакеты выделяются по реальным обязанностям, без обязательного
пакета для каждой сущности. Интерфейсы вводятся там, где нужен контракт потребителю, а не ради
архитектурного шаблона. Не переносить механически подходы Java/C#, не вводить сложный DI,
рефлексию, метапрограммирование и обобщения без веской причины. Дженерики не являются целью
сами по себе.

Ошибки обрабатываются явно, с полезным контекстом и без утечки секретов. Контексты передаются
операциям, поддерживающим отмену; запросы и фоновые операции имеют ограниченные сроки. Нельзя
прятать сетевую операцию без таймаута за интерфейсом.

Вся проектная документация, комментарии в коде и документационные комментарии к пакетам, типам,
функциям и методам пишутся по-русски. Идентификаторы, имена пакетов, файлов и технических
сущностей — по-английски. Комментарии объясняют назначение, контракт, ограничения и неочевидные
причины, не пересказывают код. Официальные лицензии и уведомления сторонних авторов сохраняются
в оригинале.

Каждая константа обязательно имеет короткий русский комментарий о назначении. Это относится
к экспортируемым, внутренним и локальным константам, включая тесты. В группе const
комментируется каждый элемент; общего комментария к группе недостаточно. Единицы измерения
и смысл ограничения уточняются при необходимости, без пересказа значения.

Аналогично аннотируются значения с постоянным назначением: sentinel errors, неизменяемые
таблицы, встроенные ресурсы, переменные сборки и фиксированные настройки. Постоянные параметры
Makefile и Dockerfile также комментируются. Обычные рабочие переменные и тривиальные литералы
в условиях не требуется превращать в константы ради комментария.

Каждое поле структуры обязательно сопровождается коротким русским комментарием о назначении
рядом с объявлением. Это относится также к вспомогательным типам и анонимным структурам в
тестах. Существенную семантику нулевого значения уточняйте в том же комментарии, без пересказа
всей модели.

```go
SourceID int64 // Источник, которому принадлежит снимок.
```

Комментарий метода, реализующего интерфейс, называет точный интерфейс и тип. Дополнительное
описание требуется только для существенных особенностей реализации, например конкретного
способа хранения. Для вспомогательных методов достаточно:

```go
// LogValue реализует интерфейс slog.LogValuer для Block.
// String реализует интерфейс fmt.Stringer для PageStatus.
```

## Принято: читаемость исходников

Markdown переносится по словам до 95 символов, SQL — до 80. Ширина считается в символах, а не
байтах. Исключения нужны только там, где перенос нарушает содержимое или форматирование:
например, таблицы Markdown и неделимые ссылки. Списки сохраняют вложенность, блоки кода —
синтаксис, значимые разрывы строк — назначение.

SQL-файлы содержат короткие русские комментарии о назначении команды или логического блока.
Самостоятельные команды и смысловые группы отделяются пустыми строками. Длинные встроенные
запросы оформляются многострочными литералами без изменения строковых значений и параметров.
Общий предел ширины Go-кода не устанавливается.

Имя обычной ошибки — err; при одновременном использовании нескольких ошибок допустимы sqliteErr
и другие понятные уточнения. Имена локальных переменных объясняют назначение. Короткие имена
допустимы для тривиальных случаев и небольших функций с очевидным контекстом; распространённые
сокращения ctx, tx, db, res и id сохраняются. Переименования учитывают область видимости и
затенение.

## Принято: зависимости и логирование

Библиотеки выбираются непосредственно перед соответствующей функциональностью. Проверяются
зрелость, поддержка, совместимость с Go, сборкой без CGO и AGPL v3. Зависимость должна решать
конкретную задачу; заранее добавлять SQLite-, Telegram-, WebAuthn- или Markdown-библиотеки не
требуется.

Логирование — через `log/slog`. Основные сущности приложения обязаны реализовывать интерфейс
`slog.LogValuer`. Для вспомогательных типов, DTO, параметров операций и других служебных
структур реализация не обязательна. Перечень основных сущностей, реализующих интерфейс,
формируется по мере реализации модели; исчерпывающий список заранее не устанавливается.

Метод `LogValue` должен возвращать компактный и безопасный набор значимых атрибутов сущности,
например идентификатор и тип. Не включать секреты, токены, содержимое материалов,
чувствительные параметры конфигурации и другие потенциально конфиденциальные данные. Не
логировать сущность целиком автоматически.

Журнал действий из [auth.md](auth.md) не следует считать автоматически обеспеченным
техническими логами. Политику хранения и доступ к нему определить при реализации.

## Принято: Git

[Репозиторий](https://github.com/ruwcs/wcs-guide) публичный. `main` — ветка по умолчанию и
релизное состояние; `dev` — повседневная разработка. После клонирования для обычной работы
нужно переключиться в `dev`.

Короткие рабочие ветки при необходимости направляются в `dev`, а не в `main`. Обязательная
сложная модель ветвления не вводится. Состояние первоначальной подготовки репозитория отражено
в [roadmap.md](roadmap.md).

Никогда не создавать коммиты и не выполнять push без прямого указания пользователя на
соответствующее действие. Просьба изменить файлы или выполнить задачу не является разрешением
на commit или push. Это постоянное правило закреплено в [AGENTS.md](../AGENTS.md).

После прямого указания создать коммиты группируйте изменения по смыслу: один коммит — логически
цельное изменение. Независимые задачи разделяйте; связанные код, тесты и документация могут
входить в один коммит. Не объединяйте всю рабочую копию автоматически и не дробите изменения
механически по файлам.

Не сливать в `main`, не создавать релизные теги и не публиковать релизы без явного указания
владельца. Не выполнять force push и деструктивные операции Git без явного согласования. Перед
изменениями проверять состояние дерева и не перезаписывать чужую работу. Порядок релиза
находится в [releases.md](releases.md).

Секреты, рабочие конфигурации, реальные БД, Telegram-сессии и снимки не включаются в Git даже
временно. Для примеров и тестов используются синтетические или специально разрешённые
обезличенные данные. `.gitignore` снижает риск случайного добавления, но не защищает уже
отслеживаемые файлы и не заменяет просмотр diff.

## Принято: проверки

Для изменений документации проверяются полнота, согласованность, локальные ссылки, сохранность
официальной лицензии и отсутствие секретов. Форматирование отслеживаемых изменений проверяется
через `git diff --check`; неотслеживаемые файлы нужно проверить отдельно без добавления в
индекс. Не создавать `go.mod`, тесты и инструменты ради формального запуска Go-команд.

После появления Go-кода минимальные проверки, применимые к изменению:

```sh
gofmt -l .
CGO_ENABLED=0 go test ./...
CGO_ENABLED=0 go vet ./...
```

Вывод `gofmt -l` должен быть пустым; форматирование исправляется до коммита. Дополнительные
проверки назначаются по риску изменения. Проверка гонок выполняется отдельно в подходящем
окружении: race detector не является частью обязательной сборки без CGO.

Тестируются значимые контракты: отсутствие новой версии при неизменившемся источнике,
сохранение последнего результата при ошибке, безопасный вывод, конкурентное использование
приглашения, отзыв доступа и согласованность публикации. Сценарии приёмки редакционного
жизненного цикла и публичного представления приведены в [roadmap.md](roadmap.md). Высокий
процент покрытия не является самостоятельной целью. В отчёте указываются выполненные проверки и
то, что пока невозможно проверить.

## Решить перед реализацией

Минимальную структуру пакетов и команд, зависимости, команды локального запуска, конфигурацию и
конкретные проверки добавлять вместе с работающей функциональностью. Dockerfile, workflows и
миграции создаются на соответствующем этапе реализации; инструкции запуска должны описывать
доступное поведение. Порядок и состояние этапов находятся в [roadmap.md](roadmap.md).

## Реализованный доменный пакет

Go-модуль и `internal/domain` созданы без сторонних зависимостей. Для пакета применяются
перечисленные выше gofmt, тесты и vet с CGO_ENABLED=0. Извлечение и рендеринг не входят в
пакет. Комментарии типов и методов описывают контракты на русском языке.

## Реализованное SQLite-хранилище

internal/storage использует единственный драйвер modernc.org/sqlite v1.62.0 (BSD-3-Clause)
через database/sql, без CGO. Версии фиксируются go.mod/go.sum; modernc.org/libc обновляется
только согласованно с драйвером. Уведомления зависимостей сохраняются при распространении
образов. Миграционная библиотека, ORM и генераторы не используются.

Open(ctx, filename) принимает только путь файловой БД; каталог должен существовать и разрешать
создание журналов. Новые БД создаются с правами 0600. Рекомендуются закрытый каталог 0700 и
локальная файловая система; права существующих файлов приложение не меняет. В Docker сохранять
каталог вне контейнера. Выбранный rollback journal может создавать файл -journal; -wal/-shm не
используются.

SQL-миграции из internal/storage/migrations встроены через embed и применяются последовательно.
Версия хранится в PRAGMA user_version; каждая миграция и её версия фиксируются атомарно.
Повторное открытие пропускает применённые версии; более новая БД вызывает ErrSchemaTooNew.
Каталог миграций проверяется на последовательность нумерации. Downgrade и автоматическое
удаление данных отсутствуют.

Пустая БД версии 0 инициализируется миграцией 001. Непустая экспериментальная БД версии 0,
включая прежнюю storage_meta, отклоняется с ErrSchemaIncompatible без переноса и удаления
данных.

Новая миграция нужна тогда и только тогда, когда схема отличается от предыдущего публичного
релиза: тега vX.Y.Z на коммите в main. До первого такого релиза есть только изменяемый
001_initial.sql, версия схемы остаётся 1. Все изменения вносятся в этот файл без добавления
миграций. После релиза опубликованные миграции неизменяемы; изменения схемы следующего
релиза накапливаются в одной новой неопубликованной миграции. Если изменений схемы нет,
миграция не создаётся. Отдельные коммиты, задачи и промежуточные сборки не являются релизами.

Совместимость промежуточных экспериментальных схем не гарантируется. В частности, БД с
прежней экспериментальной версией 2 отклоняется как более новая без изменения данных.
Автоматически понижать версию, удалять или пересоздавать такие БД нельзя.

Используется одно соединение с foreign_keys=ON, busy_timeout=5000, synchronous=EXTRA и rollback
journal DELETE. Режим существующей БД проверяется без автоматического переключения. Настройки
соединения задаются драйвером также при его замене. withTx применяет BEGIN IMMEDIATE к чтению и
записи: это простая сериализация коротких операций; внешний писатель может вызвать ожидание.
Транзакции не удерживаются во время сети и обработки материалов. Драйвер v1.62.0 самостоятельно
откатывает неудачный COMMIT; работоспособность соединения после нарушения отложенного FK
закреплена интеграционным тестом.

Для простой резервной копии остановить приложение, закрыть все соединения и копировать
согласованную БД. Если остался hot journal после аварии, сначала дать SQLite выполнить
восстановление, затем закрыть БД; произвольное удаление журнала недопустимо. Online backup
следует строить на штатном SQLite Backup API. Копирование открытого файла не гарантируется.
Восстановление проверять на копии через Open, PRAGMA integrity_check, foreign_key_check и
чтение контрольных материалов.

API возвращает ErrNotFound, ErrUnique, ErrConflict, ErrSchemaIncompatible, ErrSchemaTooNew;
domain.ErrInvalid и ошибки контекста остаются распознаваемыми через errors.Is. Причины SQLite
доступны через errors.As/Unwrap, внешние сообщения не включают SQL-параметры или материалы.
Хранилище не логирует SQL и каждую ошибку. Интеграционные тесты используют настоящую SQLite во
временных каталогах.


## Принято: семантические тесты Markdown

Тесты internal/content используют github.com/yuin/goldmark v1.8.7 (MIT): CommonMark 0.31.2,
AST и расширение Strikethrough. Библиотека написана на Go, не требует CGO и сторонних модулей;
версия закреплена в go.mod/go.sum. Импорты находятся только в _test.go. Полный GFM, Linkify,
типографические преобразования и WithUnsafe не включаются. Уведомление MIT сохраняется при
распространении соответствующих материалов.

Goldmark — основной кандидат для будущего HTML-рендерера, но его производственная интеграция
не реализована. Проверки AST и тестовый HTML не заменяют последующую проверку публичного
рендеринга. Тесты не должны скрывать ошибки конвертера фильтрацией опасных элементов парсером:
для обычного исходного текста дополнительно проверяется отсутствие RawHTML/HTMLBlock в AST.


## Принято: нативный запуск приложения

Требуются Go 1.27.x и Make; Makefile совместим с Make 3.81 и POSIX shell. Docker локально
не собирается, не запускается и не тестируется, в том числе через compose config.

```sh
mkdir -p -m 700 data
cp -n .env-example .env.dev
make run
```

Каталог data и .env.dev подготавливаются вручную один раз; cp -n сохраняет существующий файл.
Далее достаточно make run. .env.dev — доверенный shell-фрагмент: NAME=value, комментарии и
shell-кавычки.
Файл загружает только make run через shell с экспортом переменных. Значения файла заменяют
одноимённые унаследованные переменные; отсутствующие остаются унаследованными. Приложение
dotenv не читает. Не используйте недоверенные shell-команды в файле и не включайте shell trace.

| Переменная | Назначение | Требования |
|---|---|---|
| BASE_URL | Канонический внешний URL | Обязательный http/https URL в корне домена |
| DB_PATH | Файл SQLite | Обязательный файловый путь, каталог существует |

Приложение не подставляет значения по умолчанию. В Docker DB_PATH уже задан через ENV
образа; локально он задаётся в .env.dev. Пустые и некорректные параметры прекращают запуск.
BASE_URL не
определяется по Host и X-Forwarded-*. Префикс переменных не используется. SQLite URI и
:memory: не поддерживаются; база не сбрасывается автоматически.

HTTP слушает :8080 (все интерфейсы), shutdown timeout равен 10 секундам. Эти параметры не
конфигурируются. Служебных команд serve/version/help нет: бинарник запускается без аргументов.
Любые аргументы пока возвращают код 2; критические ошибки — 1, штатная остановка — 0.

Логирование — стандартный slog.Default() в stderr, текст от INFO, включая WARN и ERROR.
Уровень и формат не настраиваются. Компонент обозначается в сообщении: [app], [http],
[storage].
Конфигурация целиком, секреты и материалы не выводятся. Версия журналируется при старте.
internal/config/version.go содержит закрытую строку version
и функцию Version(); локальный go run использует dev без linker flags. Версию для production
назначает Dockerfile. Параметр -buildvcs=false отключает автоматическое включение
Git-метаданных.

| Цель Makefile | Назначение |
|---|---|
| run | Запустить go run с .env.dev и CGO_ENABLED=0; цель по умолчанию |
| test | Выполнить CGO_ENABLED=0 go test ./... |

Makefile не создаёт bin и не сохраняет бинарник. Локальная инфраструктура минимальна:
стандартные инструменты вызываются напрямую, дополнительные цели и обёртки не создаются
без подтверждённой необходимости. Форматирование и статический анализ выполняются напрямую:

```sh
gofmt -w cmd internal
CGO_ENABLED=0 go vet ./...
```

SIGINT/SIGTERM инициируют graceful shutdown с отдельным контекстом. При превышении 10 секунд
HTTP закрывается принудительно и процесс возвращает ошибку. Хранилище закрывается после HTTP.
Health GET/HEAD /healthz подтверждает начальную инициализацию и обработку HTTP, но не выполняет
проверку БД на каждый запрос. Остальные пути возвращают 404.
