# Релизы и распространение

## Принято: версии и разрешение на выпуск

Проект использует [Semantic Versioning](https://semver.org/); Git-теги имеют вид
`vMAJOR.MINOR.PATCH`. Релизное состояние находится в `main`, разработка — в `dev`. Слияние в
`main`, создание релизного тега и публикация релиза выполняются только по явному указанию
владельца, а не автоматически при завершении задачи.

Никогда не создавать коммиты и не выполнять push без прямого указания пользователя на
соответствующее действие. Описанный ниже порядок релиза сам по себе не даёт такого разрешения;
действует правило из [AGENTS.md](../AGENTS.md).

Состояние реализации релизных средств отражено в [roadmap.md](roadmap.md). Dockerfile и
workflows создаются вместе с собираемым приложением. Выпуск требует готового приложения и
выполнения проверок ниже; версия документации сама по себе не является релизом приложения.
Записи о следующей версии накапливаются в разделе `Unreleased` файла
[CHANGELOG.md](../CHANGELOG.md); их отбор и краткость определяются
[правилами CHANGELOG в AGENTS.md](../AGENTS.md).

## Принято: будущий порядок релиза

1. Подготовить `CHANGELOG.md`: перенести выпускаемые изменения из `Unreleased` в раздел версии
   с датой, сохранить новый `Unreleased`.
2. Проверить чистоту состояния, состав исходников, лицензии, актуальность документации,
   выполнить тесты и необходимые проверки по [development.md](development.md).
3. По явному указанию слить подготовленные изменения из `dev` в `main` и проверить итоговый
   коммит.
4. Создать тег `vMAJOR.MINOR.PATCH` на соответствующем коммите `main`; отправить изменения и
   тег в GitHub. Релизные теги не передвигаются; исправление требует новой версии.
5. GitHub Actions проверяет, что тег относится к релизному коммиту `main`, собирает именно его
   с `CGO_ENABLED=0` и публикует Docker-образ.
6. Проверить соответствие версии, коммита, метаданных, публичных исходников и опубликованного
   образа; при первой публикации отдельно настроить публичность GHCR.

Изменения релизной документации должны быть доступны и дальнейшей работе в `dev`; способ
согласованного переноса выбирается при выпуске без переписывания истории. Сам релиз не означает
разрешения на автоматический деплой VPS.

## Принято: GHCR и метаданные

Образ публикуется в `ghcr.io/ruwcs/wcs-guide` и скачивается без авторизации. Обязателен полный
версионный Docker-тег `vMAJOR.MINOR.PATCH`. Если добавлен `latest`, он указывает на последний
стабильный релиз и не обновляется prerelease-сборками. Дополнительные теги и целевые платформы
выбираются при реализации публикации.

Метаданные образа согласно [OCI](https://specs.opencontainers.org/image-spec/annotations/):

| Ключ | Значение |
|---|---|
| `org.opencontainers.image.source` | `https://github.com/ruwcs/wcs-guide` |
| `org.opencontainers.image.version` | Выпущенная версия с тегом `vMAJOR.MINOR.PATCH` |
| `org.opencontainers.image.revision` | Полный хеш исходного коммита |
| `org.opencontainers.image.licenses` | `AGPL-3.0-only` для кода WCS Guide; сторонние уведомления сохраняются отдельно |

GitHub Actions использует `GITHUB_TOKEN`, а не постоянный персональный токен. Для задачи
публикации образа достаточно `contents: read` и `packages: write`; другим задачам запись в
packages не нужна. Дополнительные разрешения не выдаются заранее. Публикация GitHub Release,
если будет автоматизирована отдельно, потребует отдельного рассмотрения прав. Основание —
[документация GitHub](https://docs.github.com/en/packages/managing-github-packages-using-github-actions-workflows/publishing-and-installing-a-package-with-github-actions).

### Публичность после первой публикации

Публичный репозиторий не гарантирует публичность нового пакета. Администратор открывает
организацию `ruwcs` → Packages → пакет `wcs-guide` → Package settings → Danger Zone → Change
visibility → Public. Если переключение запрещено политикой организации, сначала требуется
устранить это ограничение администратором организации.

Проверить доступ workflow к пакету через связь с репозиторием или Manage Actions access. После
настройки проверить скачивание версионного образа с чистой Docker-конфигурацией без учётных
данных GHCR. Проверку не проводить через `docker logout` в рабочем профиле пользователя.

GitHub предупреждает, что перевод пакета в Public необратим. Видимость пакета и репозитория —
разные настройки. См.
[управление доступом и видимостью GitHub Packages](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility).

## Принято: AGPL и соответствующие исходники

Код приложения лицензирован по GNU AGPL version 3 (`AGPL-3.0-only`), без отдельно
предоставленного разрешения на последующие версии. [LICENSE](../LICENSE) содержит полный
официальный неизменённый текст. Он не определяет лицензию импортируемых материалов; их условия
устанавливаются правообладателями и источниками.

Публичный [основной репозиторий](https://github.com/ruwcs/wcs-guide) предоставляет исходники
каждого релиза по соответствующему тегу. Отдельные архивы на VPS, дополнительный публичный
репозиторий и включение исходников в образ не требуются. В отличие от отдельного экспорта
релизов, публичный репозиторий также раскрывает историю разработки; секретов и рабочих данных в
ней быть не должно.

Перед распространением образа проверяется, что опубликованный коммит действительно содержит
соответствующий код, необходимые материалы сборки, установки и запуска, включая будущий
Dockerfile, инструкции, закреплённые зависимости и требуемые лицензиями уведомления. Для
зависимостей отдельно проверяются доступность необходимых соответствующих исходников и
обязательства их лицензий. Ссылка на репозиторий сама по себе не заменяет проверку полноты
комплекта. При выявлении недостающих материалов распространение откладывается до исправления.
Основание — [GNU AGPL, разделы 1, 6 и 13](https://www.gnu.org/licenses/agpl-3.0.html).

Ссылки на соответствующие исходники должны быть доступны без авторизации из описания пакета и
приложения. Не удалять и не менять опубликованные теги и необходимые исходники, пока
соответствующие образы распространяются. Рабочие БД, секреты и агрегируемые материалы не нужны
для воспроизведения программного кода и не включаются в исходный комплект.

## Принято: связь с запущенной версией

В подвале публичного сайта отображаются версия приложения, лицензия со ссылкой и ссылка на
исходники запущенной версии. Метаданные приложения и образа происходят из одного исходного
коммита, а не из переменной, произвольно обозначающей другую версию.

Релизная ссылка ведёт на `https://github.com/ruwcs/wcs-guide/tree/vMAJOR.MINOR.PATCH`;
revision позволяет проверить точный коммит. Для нерелизной сборки из чистого опубликованного
коммита показываются признак разработки и ссылка на его полный хеш. Не выдавать изменённую
локальную сборку за исходники опубликованного тега; публично развёрнутая изменённая версия
должна предоставлять соответствующие изменения пользователям согласно AGPL.

Способ передачи версии при сборке и формат отображения принимаются при реализации.

Публичный релиз для правил миграций — тег vX.Y.Z на коммите в main. Только изменение схемы
относительно предыдущего публичного релиза требует новой миграции; при неизменной схеме её
не создают. До первого релиза редактируется единственный 001_initial.sql без повышения
версии БД. После релиза опубликованные миграции неизменяемы; изменения следующего релиза
накапливаются в одной новой неопубликованной миграции. Промежуточная сборка не фиксирует
миграции. Их применение и изменение user_version остаются атомарными.
Порядок открытия и отказ от поддержки экспериментальной схемы описаны в
[правилах разработки](development.md#реализованное-sqlite-хранилище).
