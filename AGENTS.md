# Инструкции для агентов

## Обязательные правила

- Перед изменениями прочитайте [README](README.md) и профильные документы из списка ниже.
  Различайте принятые решения, предпочтения и отложенные вопросы. Изменение принципиального
  решения согласуйте с пользователем.
- При изменении поведения приложения актуализируйте относящуюся к нему документацию. Изменения
  принятых архитектурных решений фиксируйте в соответствующем профильном документе. При
  противоречии между документацией и реализацией выясните причину: ни одна из сторон не
  считается автоматически правильной.
- В разделе `Unreleased` файла [CHANGELOG.md](CHANGELOG.md) фиксируйте только факты, значимые
  для внешнего наблюдателя: что изменилось в новой версии и зачем она выпущена. Пишите
  максимально коротко и на уровне возможностей и поведения продукта. Не пересказывайте коммиты
  и внутренние этапы разработки.
- По мере реализации обновляйте состояние этапов и критериев готовности в
  [roadmap.md](docs/roadmap.md). Не описывайте ещё не реализованную функциональность как
  существующую.
- Никогда не создавайте коммиты и не выполняйте push без прямого указания пользователя на
  соответствующее действие. Просьба изменить файлы или выполнить задачу не является разрешением
  на commit или push.
- Разбивайте изменения на логически цельные коммиты по смыслу. Независимые изменения
  разделяйте; связанные код, тесты и документация могут входить в один коммит. Количество
  файлов само по себе не определяет границы коммита.
- Разрабатывайте в `dev`. Не сливайте в `main`, не создавайте релизные теги и не публикуйте
  релизы без явного указания. Force push и деструктивные операции Git требуют явного
  согласования. Сохраняйте чужие незакоммиченные изменения.
- Документация, комментарии и документационные комментарии к Go-коду — на русском;
  идентификаторы, пакеты, файлы и технические имена — на английском. Официальный текст
  `LICENSE` и уведомления третьих сторон не переводите и не изменяйте.
- Каждая константа, включая локальные и тестовые, обязательно аннотируется коротким русским
  комментарием о назначении. В const-группах комментируйте каждый элемент, а не только группу.
  То же правило действует для аналогов констант: sentinel errors, неизменяемых таблиц,
  встроенных ресурсов, переменных сборки и фиксированных настроек. Постоянные параметры
  Makefile и Dockerfile также аннотируются; единицы и смысл ограничений поясняются по мере
  необходимости. Не заменяйте обычные рабочие переменные и тривиальные литералы константами
  исключительно ради комментариев.
- Каждое поле структуры, включая вспомогательные и анонимные структуры в тестах, сопровождайте
  коротким русским комментарием о назначении рядом с объявлением. Для метода, реализующего
  интерфейс, указывайте интерфейс и тип:
  `// LogValue реализует интерфейс slog.LogValuer для Block.` Дополнительные пояснения нужны
  только при существенных особенностях реализации.
- Документацию для человека пишите компактно и лаконично. Документацию для агента пишите
  подробно: включайте контекст, требования, ограничения и принятые решения, достаточные для
  самостоятельной работы без исходного обсуждения.
- Следуйте идиоматическому Go: простые пакеты, явные ошибки, корректные контексты и таймауты.
  Не вводите интерфейсы, фреймворки, рефлексию, дженерики или инфраструктуру без практической
  необходимости.
- Инфраструктуру делайте минимальной: используйте стандартные инструменты напрямую.
  Дополнительные команды, настройки и обёртки добавляйте только при подтверждённой нужде.
  Для локального запуска используйте go run, для тестов — go test; отдельные локальные
  сборки и сохранение бинарника не нужны. Makefile содержит только run и test.
- Новая миграция нужна тогда и только тогда, когда схема меняется относительно предыдущего
  публичного релиза — тега vX.Y.Z на коммите в main. До первого такого релиза существует
  только 001_initial.sql: изменяйте его, не создавайте новых миграций и не повышайте версию БД.
  После релиза опубликованные миграции неизменяемы; изменения следующего релиза накапливайте
  в одной новой неопубликованной миграции. Коммиты, задачи и промежуточные сборки не являются
  основанием для новых миграций. Подробности — в правилах разработки.
- Go 1.27, module path `github.com/ruwcs/wcs-guide`, SQLite без CGO; приложение обязано
  собираться с `CGO_ENABLED=0`. Зависимости выбирайте непосредственно перед реализацией с
  проверкой поддержки и совместимости лицензий.
- Для логирования используйте `log/slog`. Основные сущности обязаны реализовывать
  `slog.LogValuer`; границы требования и безопасный состав атрибутов описаны в
  [правилах разработки](docs/development.md).
- При импорте сохранение информации важнее оформления. Конфликтующую декорацию упрощайте
  с диагностикой, сохраняя текст и значимые ссылки. Намеренно скрытое содержимое не
  раскрывайте:
  спойлеры заменяются пометкой без исходного текста и связанных адресов.
- Локально Docker не собирайте, не запускайте и не тестируйте, включая compose config.
  Dockerfile и production Compose проверяются только по содержимому; VPS не затрагивается.
- Каркас запускается без служебных CLI-команд. BASE_URL и DB_PATH обязательны, без префикса.
  HTTP :8080, shutdown 10 секунд, текстовые slog-логи от INFO фиксированы в коде.
- Не обращайтесь к внешним источникам из обработчика публичного запроса. Не теряйте оригиналы и
  последний успешный результат при временных ошибках. Импортируемый контент недоверенный.
- Не помещайте секреты, токены, cookies, Telegram-сессии, рабочие БД, конфигурации окружений и
  реальные снимки контента в Git, логи и образы. `.gitignore` не заменяет проверку изменений
  перед коммитом.
- Проверяйте значимое поведение и выполняйте подходящие изменению проверки. После появления
  Go-кода используйте `gofmt`, `go test` и `go vet` с CGO_ENABLED=0. Не пишите тесты ради
  покрытия. В отчёте указывайте результат и ограничения проверок.
- Не реализуйте будущие возможности и заготовки ради структуры. Код, пакеты, зависимости и
  инфраструктурные файлы создавайте вместе с функциональностью, которой они необходимы.

- Markdown переносите по словам до 95 символов в строке. Исключения — конструкции, перенос
  которых нарушает форматирование или содержимое: таблицы, неделимые ссылки и отдельные
  фрагменты кода. Сохраняйте отступы и значимые разрывы строк.
- SQL оформляйте строками до 80 символов, кроме неделимых конструкций. Перед командой или
  логическим блоком пишите краткий русский комментарий о назначении; самостоятельные команды и
  смысловые группы разделяйте пустыми строками.
- Обычную ошибку называйте err, не e; для одновременно используемых ошибок допустимы уточнения
  вроде sqliteErr. Локальные переменные называйте по назначению. Короткие имена оставляйте для
  очевидных небольших областей видимости, счётчиков и общепринятых сокращений (i, j, ctx, tx,
  db, res, id).
