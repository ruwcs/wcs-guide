# Инструкции для агентов

## Обязательные правила

- Перед изменениями прочитайте [README](README.md) и профильные документы из списка ниже. Различайте принятые решения, предпочтения и отложенные вопросы. Изменение принципиального решения согласуйте с пользователем.
- При изменении поведения приложения актуализируйте относящуюся к нему документацию. Изменения принятых архитектурных решений фиксируйте в соответствующем профильном документе. При противоречии между документацией и реализацией выясните причину: ни одна из сторон не считается автоматически правильной.
- Значимые изменения приложения отражайте в разделе `Unreleased` файла [CHANGELOG.md](CHANGELOG.md). По мере реализации обновляйте состояние этапов и критериев готовности в [roadmap.md](docs/roadmap.md). Не описывайте ещё не реализованную функциональность как существующую.
- Никогда не создавайте коммиты и не выполняйте push без прямого указания пользователя на соответствующее действие. Просьба изменить файлы или выполнить задачу не является разрешением на commit или push.
- Разрабатывайте в `dev`. Не сливайте в `main`, не создавайте релизные теги и не публикуйте релизы без явного указания. Force push и деструктивные операции Git требуют явного согласования. Сохраняйте чужие незакоммиченные изменения.
- Документация, комментарии и документационные комментарии к Go-коду — на русском; идентификаторы, пакеты, файлы и технические имена — на английском. Официальный текст `LICENSE` и уведомления третьих сторон не переводите и не изменяйте.
- Документацию для человека пишите компактно и лаконично. Документацию для агента пишите подробно: включайте контекст, требования, ограничения и принятые решения, достаточные для самостоятельной работы без исходного обсуждения.
- Следуйте идиоматическому Go: простые пакеты, явные ошибки, корректные контексты и таймауты. Не вводите интерфейсы, фреймворки, рефлексию, дженерики или инфраструктуру без практической необходимости.
- Go 1.27, module path `github.com/ruwcs/wcs-guide`, SQLite без CGO; приложение обязано собираться с `CGO_ENABLED=0`. Зависимости выбирайте непосредственно перед реализацией с проверкой поддержки и совместимости лицензий.
- Для логирования используйте `log/slog`. Основные сущности обязаны реализовывать `slog.LogValuer`; границы требования и безопасный состав атрибутов описаны в [правилах разработки](docs/development.md).
- Не обращайтесь к внешним источникам из обработчика публичного запроса. Не теряйте оригиналы и последний успешный результат при временных ошибках. Импортируемый контент недоверенный.
- Не помещайте секреты, токены, cookies, Telegram-сессии, рабочие БД, конфигурации окружений и реальные снимки контента в Git, логи и образы. `.gitignore` не заменяет проверку изменений перед коммитом.
- Проверяйте значимое поведение и выполняйте подходящие изменению проверки. После появления Go-кода используйте `gofmt`, `go test`, `go vet` и сборку без CGO. Не пишите тесты ради покрытия. В отчёте указывайте результат и ограничения проверок.
- Не реализуйте будущие возможности и заготовки ради структуры. Код, пакеты, зависимости и инфраструктурные файлы создавайте вместе с функциональностью, которой они необходимы.
